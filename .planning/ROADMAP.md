# Roadmap: Wayland Nano Verified Change

## Overview

This milestone promotes the approved Wayland Nano 0.2 verified-change program through seven serial work-package waves. It begins with frozen contracts, then closes memory and PDF hardening, builds the gate/receipt foundation and climb engine, exposes the verifier through the CLI, and finishes with sealed Gate Cards dogfooded through that verifier. WP-0.1 remains an owner-host-run handoff only. Autonomous work stops after WP-4; WP-5, WP-6, and all deferred capabilities are not scheduled.

## Milestone

**Wayland Nano 0.2 Verified Change**

### Phase 1: WP-0.4 Frozen Contracts and Program Controls

**Goal**: Operators have four drift-protected contract artifacts and an enforceable, evidence-backed promotion process for every executable WP, while WP-0.1 remains an explicit owner-host-run handoff.
**Depends on**: Nothing (first promotion wave)
**Requirements**: CTRL-01, CTRL-02, CTRL-03, CTRL-04, CTRL-05, CTRL-06, CTRL-07, CTRL-08, HOST-01, CTR-01, CTR-02, CTR-03, CTR-04, CTR-05, CTR-06
**Success Criteria** (what must be TRUE):

  1. Operators can inspect four byte-canonical JSON contracts for capability profile, journal semantics, all six Flux endpoints, and event vocabulary/counts, each with freeze and change-control metadata.
  2. Regeneration is byte-identical, and both generator checks and workspace schema tests visibly reject stale, tampered, or fixture-invalid contract artifacts.
  3. The WP-0.4 executor stays within its explicit additive ownership, reports G-CTR-1 ready for owner closure without self-approval, and records WP-0.1 as an unexecuted interactive Windows handoff.
  4. Every subsequent WP can be promoted from a recorded current `origin/master` SHA in its canonical isolated branch/worktree with ownership, secret, provenance, generated-artifact, I/R/L, and one-line evidence rules explicit.
  5. A WP cannot advance until its Critical/High audit, bounded fix round, local gate, no-ff integration gate, push, and green CI result are recorded.

**Promotion Gate**:

### Phase 4: WP-1 Gate and Receipt Foundation

### Phase 5: WP-2 Gated Climb

**Goal**: Users can drive a bounded verified-change climb that ratchets on executable evidence while exposing only opaque failing-check identifiers.
**Depends on**: Phase 4 (WP-1 `nano-verify` foundation promoted and CI green)
**Requirements**: CLIMB-01, CLIMB-02, CLIMB-03, CLIMB-04, CLIMB-05
**Success Criteria** (what must be TRUE):

  1. A climb proceeds through probe, ensemble, per-check surgical escalation, and one consolidation-on-plateau path using the injected Effects seam.
  2. A candidate advances only on strict score improvement or a strict failure-set subset; equal-count oscillating failures never ratchet.
  3. Builders and reviewers see only opaque canonical failing-check identifiers, never gate source, command, expected values, fixtures, or ambient secrets.
  4. Every model call consumes the default 12-call budget, escalation is typed, and every completion maps to the canonical terminal and stop enums.
  5. The driver-stub battery visibly covers wins, rejects, accepts, consolidation, plateau, exhaustion, budget, leakage, oscillation, and terminal completeness.
